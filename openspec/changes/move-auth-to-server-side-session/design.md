## Context

动机见 [proposal.md](proposal.md)。当前 `app/auth.py` 已从用户表建立身份并核对 role、class_id、session_version；材料路由已有教师权限和班级过滤。本 change 只替换会话存储方式，继续使用这些校验。

当前 Flask + sqlite3 + Docker Compose 是单应用、单 worker。工厂/导入不建库，`scripts/serve.py` 在启动前准备数据库。现有测试约定 8 小时期限、退出使同账号全部设备失效、CSRF 和安全 Cookie 属性，这些均保留。

正式 specs 尚为空；本 capability 补充 `add-class-scoped-material-library` 中的行为契约，替代其 signed-cookie/no Session entity 设计决定，不修改旧 change。

## Goals / Non-Goals

**Goals:**

- SQLite 保存 Session，浏览器只持有随机标识；复用现有 session 字典、用户核验和材料权限逻辑。
- 用少量读写操作实现登录、过期和退出，保留现有行为及测试覆盖。

**Non-Goals:**

- 不引入 Redis、ORM、额外服务、管理员或无关 UI/材料重构。
- 不实现 revision 乐观锁、冲突重试、并发调度框架、专用清理命令或后台任务。
- 不增加完整故障注入矩阵、多容器升级演练或自动回滚系统。

## Decisions

### 1. 小型 SQLite 会话接口

使用 Flask SessionInterface 接入现有 sqlite3，新增小型会话模块，在工厂注册但不在工厂连接或初始化数据库。保持现有 session 字典与 `session_transaction()` 兼容，登录后仍为 user_id、role、class_id、session_version、_permanent、csrf_token 六字段；仅在服务端用 JSON 存储。SID、到期时间和新建标记作为对象属性，不加入字典。

现有数据库仅增加一张 sessions 表：

| 字段 | 用途 |
| --- | --- |
| sid_hash TEXT PRIMARY KEY | 不透明 ID 的 SHA-256 摘要，用于查找 |
| data TEXT NOT NULL | 服务端会话 JSON 字典 |
| expires_at INTEGER NOT NULL | UTC epoch 绝对期限 |

不再增加 created_at、user_id 外键、账号索引或 revision。身份已在服务端 JSON 中，退出全部设备失效复用 users.session_version，无需再按账号批量删除会话行。保留 SHA-256 摘要只是一次标准库调用，避免数据库直接存储可重放的原始凭证，不增加协议或基础设施。

ID 使用 `secrets.token_urlsafe(32)`，接受明确的 URL-safe 格式。无效、未知或旧 signed-cookie 不能成为可信身份，也不能由请求指定 ID 创建会话。继续使用现有 session Cookie 名和安全配置，保留 SECRET_KEY 必填契约。无需 Redis/ORM；内存不能满足持久化要求，继续加密身份 Cookie 也不符合目标。

### 2. 简单的打开、保存和失效规则

- 打开：通过 Cookie ID 摘要查表并检查 expires_at，解析服务端 JSON；缺失、过期、错误格式或无效数据返回未认证状态。后续认证继续查询用户表，核对角色、班级和 session_version。数据库读故障返回通用 5xx，不回退客户端身份。
- 新建：只给服务端刚生成的 ID 执行 INSERT，登录页生成 CSRF 时可建立匿名会话。匿名会话也设置 8 小时期限。
- 保存：只保存实际修改的会话；已加载会话仅 UPDATE 仍存在且未过期的行。更新零行就放弃保存，不改为 INSERT/UPSERT，不重新发布该旧 ID。不采用 revision、比较交换或冲突重试。
- 清空：删除当前会话行并清除 Cookie。正常材料列表、上传、下载和学生拒绝请求不修改会话，也不进行全局清理。

保留这几条规则即可避免旧保存操作重新创建已删除的 ID；其他设备残留的旧记录因用户 session_version 已变化而不能授权。仅增加一个顺序模拟“读取旧会话、删除、再保存”的小测试，不建立复杂并发测试体系。已经通过认证并在执行中的业务请求不由本次变更强制中断；退出后新请求必须重新校验并被拒绝。

### 3. 登录、退出和权限复用

登录成功时清空旧数据，生成新 ID 与 CSRF，从数据库填充身份，在短事务中替换当前会话；提交后才能返回 200 和新 Cookie。轮换防止会话固定，保留这一小步骤，不引入通用并发登录协调机制。错误密码保持 401 并清除原认证身份，错误 CSRF 保持 403。

退出保持现有用户 session_version 递增，在同一短事务中删除当前会话行，成功后清除 Cookie、返回 204。其他设备旧会话在下次认证时因版本不符返回 401，不需要立即物理删除所有记录。无须为每次会话保存增加用户版本事务重查；授权前的现有数据库核验仍为必经路径。

沿用固定 8 小时期限，普通读取不续期，服务端到期检查独立于 Cookie Expires；保留 HttpOnly、SameSite=Lax、Secure 配置和现有 CSRF 顺序。teacher/student 角色不变，学生上传先被角色判断拒绝为 403；材料 SQL 班级过滤、伪造字段拒绝和返回状态均保持现状。

### 4. 启动准备与最低限度错误处理

将幂等会话表准备接入现有新库初始化及已有库启动路径，不新增迁移框架、管理 CLI 或必填环境变量。已有库只增加会话存储，不重置账号或材料。启动时执行一次按 expires_at 删除过期记录；运行期间每次读取都检查到期，因此长期不重启只会积累无效记录，不会延长授权。

复用应用普通 5xx 错误处理，不要求所有会话故障统一为 503。必要写入未提交不得发出成功登录/退出响应或新有效 Cookie，也不得把失败当作认证成功；在会话接口保存边界确保这一点。损坏会话内容可作为无效会话拒绝，不建立专门的损坏恢复流程。不输出标识、密码、哈希、CSRF 或密钥。`/health` 不需要会话，继续使用原健康检查的 200/503 和 JSON 契约。

### 5. 聚焦测试

复用全量现有测试，新增测试只覆盖本次替换存储带来的差异：

- Cookie 只有随机 ID，SQLite 存在对应数据；删除记录后 Cookie 无效；同库新应用实例可读取有效会话。
- 登录轮换、旧 Cookie 拒绝、退出/过期失效和删除后保存不会重建会话；既有 CSRF、Cookie 属性、身份版本测试继续执行。
- 补齐 A/B 两班两角色的上传、本班读取及双向越权验证，特别是学生携有效 CSRF 伪造 role=teacher 仍为 403、材料及文件不变。
- 一个新旧库准备/重复执行的数据保留测试，同时检查启动清理只影响过期记录；不额外做容器升级/回滚矩阵。
- 各一个会话读取失败和登录保存失败的代表性检查，确认无授权旁路及虚假成功；不枚举磁盘、锁竞争、损坏 JSON、各提交阶段和并发排列的故障组合。继续运行现有健康检查测试。

适配仅限新增表的精确表集合断言，以及登录前全库快照：业务无副作用快照继续覆盖全部原七张表与上传文件，会话变化单独验证。不删除、跳过或降低原业务和安全断言。新增覆盖可以并入已有测试，不要求为每个 Scenario 单独建测试文件。

## Risks / Trade-offs

- [不用 revision 时普通会话修改可能后写覆盖先写] → 认证身份由数据库核验，登录轮换 ID，已加载记录仅 UPDATE，退出用既有用户版本撤销；不扩展为通用可并发编辑的会话系统。
- [启动间隔长导致过期行积累] → 每次读取先判期限，启动时简单清理；独立维护能力不属于本轮完成条件。
- [SQLite 故障或锁竞争] → 使用短事务和显式关闭连接，通用 5xx 拒绝处理；不增加重试框架或认证降级。
- [新增表影响旧测试的结构/快照假设] → 只适配存储表现，保持业务断言完整，全量测试通过才可完成 Apply。
